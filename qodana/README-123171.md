## 1. Tabela de mapeamento

| Code Smell (Fowler) | Inspeção no IntelliJ/Qodana | ID da inspeção | Métrica / Limiar | Limitações |
|---|---|---|---|---|
| Long Method | Overly long method | `OverlyLongMethod` | Número de linhas do método; limite configurado de 30 linhas (`m_limit: 30`) | A inspeção utiliza um limite absoluto de linhas e não combina automaticamente diferentes métricas para identificar o code smell. |

O code smell *Long Method*, descrito por Martin Fowler, ocorre quando um método apresenta uma extensão excessiva, dificultando a sua compreensão, manutenção e reutilização.

Para a sua identificação foi selecionada a inspeção `OverlyLongMethod`, configurada através de um perfil personalizado do Qodana.

## 2. Configuração do Quality Gate

Foi utilizado o **Qodana for JVM Community 2024.3** para analisar o projeto Java Battleship2, com um perfil de inspeção personalizado destinado à identificação de métodos excessivamente longos.

Foram utilizados os seguintes ficheiros:

- `.github/workflows/qodana-smell-123171.yaml` — workflow individual do GitHub Actions.
- `qodana-123171.yaml` — ficheiro principal de configuração do Qodana.
- `qodana/profiles/profile-123171.yaml` — perfil personalizado para a inspeção Long Method.

O perfil personalizado foi configurado com a inspeção `OverlyLongMethod`, ativada com severidade `WARNING` e limite de 30 linhas.

O quality gate foi integrado no GitHub Actions, permitindo executar automaticamente a análise nos eventos de `push` e `pull_request` definidos no workflow.

Na configuração principal foi definido o limiar de severidade `any: 0`. No workflow, foi também utilizado o argumento `--fail-threshold 1`.

## 3. Introdução intencional do Code Smell

Para demonstrar a presença do code smell *Long Method*, foi criada uma branch específica:

`teste-smell-123171`

Nesta branch foi introduzido intencionalmente o método `testeLongMethod()` na classe `Game.java`.

O método contém um número elevado de instruções, tendo sido desenvolvido com o objetivo de ultrapassar o limite de 30 linhas estabelecido no perfil personalizado.

Esta alteração foi realizada exclusivamente para efeitos de teste e demonstração da análise estática, não correspondendo a uma funcionalidade necessária ao funcionamento do jogo Battleship2.

## 5. Verificação do Code Smell e limitações técnicas

Durante os testes realizados, foi possível observar a identificação do code smell *Long Method* através das ferramentas de análise estática utilizadas.

Contudo, devido a um problema técnico no meu computador, não foi possível conservar as evidências necessárias para documentar adequadamente essa verificação.

Foram realizadas várias execuções do Qodana através do GitHub Actions, tendo sido obtidos resultados de falha do quality gate. No entanto, os registos disponíveis não permitem demonstrar de forma inequívoca que essas falhas resultaram exclusivamente do *Long Method* introduzido.

Assim, embora tenha sido possível observar o comportamento pretendido durante os testes, não foi possível apresentar uma demonstração documental completa da comparação entre os estados anterior e posterior à correção do code smell.

## 6. Proteção da branch

Foi considerada a configuração de uma regra de proteção para a branch `main`, de forma a exigir a validação automática dos workflows antes da integração de alterações.

Contudo, a configuração não pôde ser concluída devido à ausência de permissões administrativas no repositório.

Esta limitação impediu a aplicação direta da regra de proteção solicitada.

## 7. Conclusão

Este trabalho permitiu explorar a identificação do code smell *Long Method* e a integração do Qodana num processo de integração contínua através do GitHub Actions.

Foi criado um perfil de inspeção personalizado, configurado um quality gate e introduzido intencionalmente um método longo para testar o comportamento da análise estática.

Durante os testes, foi possível observar a identificação do problema, embora dificuldades técnicas tenham impedido a conservação de todas as evidências necessárias à sua demonstração.

Apesar desta limitação, o trabalho contribuiu para compreender a importância da análise estática e da utilização de quality gates na melhoria da qualidade do software.
